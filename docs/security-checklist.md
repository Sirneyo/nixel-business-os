# Security Checklist

Work through this list before putting Nixel Business OS — Starter Edition anywhere near the public internet or real customer data. Each item is practical and short — do the paragraph, tick the box.

- [ ] **Default credentials.** The Starter Edition ships with **no default user accounts**, so there are no passwords to change — but that is because there is no login at all. Treat "add authentication" (below) as the very first job before public exposure, and change any credentials you introduce (database passwords, SMTP secrets, proxy auth) away from anything you used in testing.

- [ ] **Protect API keys.** All secrets (Anthropic key, Google Places key, SMTP password, webhook key) live only in `backend/.env`. Never commit `.env` to git (check `.gitignore` covers it), never paste keys into issues or chat, and never bake them into the frontend build. If a key leaks — or you even suspect it did — rotate it at the provider immediately and update `.env`.

- [ ] **Database permissions.** For SQLite, make sure `nixel_starter.db` is readable/writable only by the account running the backend (`chmod 600 nixel_starter.db` on Linux) and lives outside any web-served folder. For PostgreSQL, create a dedicated `nixel` database user with rights only on the `nixel_starter` database — never connect as the superuser — and don't expose port 5432 to the internet.

- [ ] **User authentication.** The starter has **no auth**: anyone who can reach the API can read and modify everything. It must not be exposed to the internet as-is. As a stopgap, put HTTP Basic Auth on the whole site at the reverse proxy (nginx: `auth_basic` + an `htpasswd` file; Caddy: `basic_auth`). For real use, add a proper auth layer — e.g. FastAPI dependency-based session or token auth on every router, or an identity-aware proxy (Authelia, Cloudflare Access) in front. Remember to exempt `POST /api/inbound/lead` from proxy auth if external forms must reach it (it has its own key check).

- [ ] **Role-based access.** Once you add auth, decide who can do what. A sensible split for a small team: admins manage settings, campaigns and automations; members work leads and the pipeline; nobody but admins can start real (non-simulated) sending. Enforce roles server-side in the routers — UI hiding alone is not access control.

- [ ] **HTTPS everywhere.** Terminate TLS at the reverse proxy (certbot with nginx, or Caddy which does it automatically — see [installation.md](installation.md)). After that, set `PUBLIC_BASE_URL` and `CORS_ORIGINS` to the `https://` URLs and never serve the API over plain HTTP publicly — the webhook key and any future session cookies travel in headers.

- [ ] **Environment-file protection.** Lock the `.env` file down to the service account: `chown nixel:nixel .env && chmod 600 .env` on Linux; on Windows, restrict the file's ACL to the service user. Don't copy `.env` into backups that are stored less securely than the server itself.

- [ ] **Input validation.** Pydantic already validates every request body: types are enforced, emails must be syntactically valid (`EmailStr`), numeric fields are range-bound (e.g. leads per run 1–100, campaign daily limit 1–2000, step delays 0–90 days), and unknown automation step kinds, triggers and pipeline stages are rejected. Email template content is escaped except for a small allow-list of inline tags. What Pydantic does *not* do: authenticate callers, rate-limit, or sanity-check business meaning (e.g. that a daily limit is wise) — those remain your job.

- [ ] **Rate limiting.** Add basic limits at the proxy so scripts can't hammer the API or brute-force the webhook key. nginx: `limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;` in `http {}`, then `limit_req zone=api burst=20 nodelay;` inside the `location /api/ {}` block. Caddy: use the `rate_limit` plugin, or front the site with a CDN/WAF that provides limits. Give `POST /api/inbound/lead` its own stricter bucket.

- [ ] **Webhook verification.** The inbound webhook is protected by a shared secret: requests must carry `X-API-Key` matching `INBOUND_WEBHOOK_KEY` (503 when unconfigured, 403 on mismatch). Generate the key with `python -c "import secrets; print(secrets.token_hex(24))"` — never something guessable. Rotate it periodically and whenever it may have leaked (it is visible to anything that could read your form-handling server). Never put the key in public client-side JavaScript — proxy form submissions through your own server (see the note in [examples/inbound-form.html](examples/inbound-form.html)).

- [ ] **Email-sending restrictions.** Before real sending: keep per-campaign `daily_limit` low (tens, not hundreds) and warm a new domain/IP up gradually over weeks; send only within business-hours windows (the campaign send window/days support this); honour opt-outs — the sample templates include a "Reply STOP" footer, and you must actually stop contacts who ask (mark the lead, remove from campaigns). Know the law for your recipients: **CAN-SPAM** (US) requires truthful headers, a physical address and a working opt-out; **GDPR** (EU) and **PECR** (UK) constrain unsolicited B2B email and require a lawful basis — get advice if unsure. Your SMTP provider will suspend you for spam complaints long before regulators call.

- [ ] **Data backups.** Nightly automated backups plus one before every update: copy the SQLite file, or `pg_dump` for PostgreSQL (commands in [installation.md](installation.md)). Store them off the server, encrypt them (they contain personal data), and test a restore.

- [ ] **Logging.** The backend logs to stdout (scheduler ticks, engine runs, unhandled errors with stack traces); under systemd use `journalctl -u nixel` to review. Keep proxy access logs to see who is hitting the API. Review logs after anything odd (403 spikes on the webhook = someone probing your key). Avoid logging secrets or full lead data at higher verbosity, and set a retention period consistent with your privacy policy.

- [ ] **Dependency updates.** Regularly run `pip list --outdated` and `pip install -U -r requirements.txt` in the backend venv, and `npm audit` / `npm audit fix` in the frontend, then retest. Subscribe to security advisories for FastAPI/uvicorn if you run this long-term. Update Python and Node themselves on the server's normal patch cycle.

- [ ] **Server security.** Standard hygiene: enable a firewall allowing only 80/443 (and your SSH port) — `ufw allow 80,443/tcp` — with the backend bound to `127.0.0.1` so port 8000 is never public; SSH by key only (`PasswordAuthentication no`), no root login; unattended security updates enabled; run the backend as a dedicated non-root user.

- [ ] **Privacy & data retention.** You are storing personal data (names, emails, notes) about people who mostly haven't asked to hear from you. Decide and document how long you keep leads, delete leads on request — the workspace supports per-lead deletion (`DELETE /api/leads/{id}`), which also removes their campaign memberships and opportunity — and remember exported CSVs and backups also contain this data. If GDPR applies to you, know your lawful basis for processing, keep a record of it, and be able to answer a subject-access request from the data you hold here.
